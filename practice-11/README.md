## Подготовка базы

Установить PostgreSQL 18.x и убедиться, что служба запущена. Проверить клиент:

```bash
psql --version
```

Под административной ролью подключиться к postgres и один раз создать роль и отдельную базу:

```sql
CREATE ROLE tip_app LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE;
\password tip_app
CREATE DATABASE tip_tasks OWNER tip_app ENCODING 'UTF8' TEMPLATE template0;
\q
```

Пароль вводится интерактивно и не сохраняется в репозитории. Если роль или база уже существует, не удалять её: проверить владельца и назначение либо выбрать другое имя учебной базы.

Подключение владельцем:

```bash
psql -X -h 127.0.0.1 -p 5432 -U tip_app -d tip_tasks
```

Внутри psql:

```sql
SELECT current_database(), current_user, version();
SHOW server_encoding;
SELECT lower('ПРОВЕР') = 'провер' AS russian_case_supported;
\q
```

Ожидаются база tip_tasks, роль tip_app, кодировка UTF8 и true в проверке кириллицы. Фактические значения записать в таблицу выше.

## Модель данных

Созданы две таблицы:

- `public.categories`: `id` и `name`;
- `public.tasks`: `id`, `title`, `completed`, `priority`, `category_id`.

Связь: одна категория может иметь 0..N задач; каждая задача относится ровно к одной категории. Внешний ключ запрещает удаление категории, на которую ссылаются задачи.

| Поле | Тип | Ограничения |
|---|---|---|
| categories.id | integer identity by default | PRIMARY KEY, > 0 |
| categories.name | text | NOT NULL, UNIQUE, 1–100 символов, без обычных пробелов по краям |
| tasks.id | integer identity by default | PRIMARY KEY, > 0 |
| tasks.title | text | NOT NULL, 1–100 символов, без обычных пробелов по краям |
| tasks.completed | boolean | NOT NULL, DEFAULT false |
| tasks.priority | text | NOT NULL, только low/medium/high |
| tasks.category_id | integer | NOT NULL, FK categories(id), ON DELETE RESTRICT |

Создан индекс `tasks_category_id_idx` на `tasks(category_id)`.

Условие длины использует `char_length`, а проверка пробелов — `btrim`. База отклоняет неверные значения; она не заменяет серверную нормализацию, которая уже реализована в ПР10. В API остаются прежние имена `categoryId`, а в SQL используется `category_id`.

## Начальные данные и identity

Вставлены исходные данные ПР10: 3 категории и 12 задач с разреженными ID 1, 4, 7, 10, 13, 16, 19, 22, 25, 28, 31, 34. Все названия, статусы, приоритеты и категории сохранены.

После явной вставки ID выполнена синхронизация последовательностей обеих identity-колонок через `pg_get_serial_sequence`, `max(id)` и `setval(..., true)`. Это обеспечивает выдачу ID больше максимального исходного: следующая новая задача после чистого seed получает 35, категория — 4.

Последовательности PostgreSQL не являются транзакционным счётчиком: откат или удаление могут оставлять пропуски. Повторное использование ID не требуется.

## Контрольные вопросы

1. **Почему категория хранится отдельно?** Это устраняет повторение её названия в каждой задаче и позволяет контролировать ссылочную целостность.
2. **Как устроена связь?** Категория имеет 0..N задач; каждая задача имеет ровно одну категорию.
3. **Почему CHECK не заменяет NOT NULL?** CHECK с NULL даёт UNKNOWN, а CHECK не запрещает UNKNOWN; NOT NULL нужен отдельно.
4. **Что защищает FK?** Нельзя ссылаться на несуществующую категорию или удалить используемую категорию.
5. **Почему RESTRICT?** Удаление категории не должно автоматически уничтожать её задачи.
6. **Чем BY DEFAULT отличается от ALWAYS?** BY DEFAULT допускает явный ID при загрузке исходных разреженных значений.
7. **Зачем setval после seed?** Явные ID в INSERT не продвигают sequence.
8. **Почему после ROLLBACK возможны пропуски ID?** Значения nextval не откатываются как обычные строки.
9. **LEFT JOIN и INNER JOIN?** LEFT JOIN сохраняет все строки левой таблицы; INNER JOIN только совпавшие пары.
10. **Почему count(t.id)?** Он не учитывает NULL-строку от LEFT JOIN, поэтому пустая категория получает 0.
11. **WHERE и HAVING?** WHERE фильтрует строки до группировки, HAVING — группы после неё.
12. **Зачем ORDER BY?** Порядок строк без него не гарантирован.
13. **char_length/btrim и JavaScript?** PostgreSQL считает символы и обрезает обычные пробелы, JS length считает UTF-16 code units, trim обрабатывает более широкий набор пробелов.
14. **Почему изменение SQL-файла не меняет базу?** SQL нужно выполнить; файл не является миграцией, пока не создан механизм версий и применения.
15. **Почему PostgreSQL пока не виден в ПР10?** Сервер ПР10 ещё использует память процесса; подключение базы — задача следующей работы.

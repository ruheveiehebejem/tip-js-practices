## Результат

Сервер ПР10 поддерживает чтение и полный CRUD. Данные хранятся в памяти процесса: обновление браузера не удаляет их, а перезапуск сервера возвращает исходный набор. React-клиент ПР8 обращается к API по HTTP и после успешных изменений повторно загружает список.

## Серверная валидация

Функция `validateTaskInput(value, { partial, categoryIds })` не использует Express и не меняет исходное тело.

**POST** требует поля title, priority и categoryId. ID назначается сервером, а completed всегда устанавливается в false. Поля id и completed запрещены в запросе POST.

**PATCH** принимает непустое подмножество title, priority, categoryId и completed. Поле id запрещено. Непереданные значения остаются прежними. В частности, `completed: false` — корректное обновление, а не отсутствие значения.

Правила полей:
- title — строка после trim длиной 1–100 символов;
- priority — только low, medium или high;
- categoryId — положительное безопасное целое число, существующее в списке категорий;
- completed — только boolean;
- любые неизвестные поля отклоняются.

Все обнаруженные ошибки собираются в одном объекте details. Для него используется объект без прототипа, чтобы имя `__proto__` не потерялось. При неверном поле никакое изменение не передаётся в store.

## Операции хранилища

`createTask(value)` создаёт объект с серверным ID, `completed:false`, нормализованным названием, приоритетом и категорией. Первый новый ID после исходного набора — 35. Счётчик увеличивается только после успешного создания.

`updateTask(id, changes)` находит запись и применяет только проверенные поля. Исходный ID сохраняется. Непереданные поля, включая completed, не меняются. При отсутствии записи возвращается null.

`deleteTask(id)` удаляет только найденную запись и возвращает true или false. Удаление не уменьшает nextId, поэтому ID не используются повторно.

Методы возвращают копии объектов и не раскрывают изменяемые ссылки хранилища. Каждый экземпляр store изолирован от других экземпляров.

## HTTP-контракт записи

| Метод | Успех | Ответ |
|---|---:|---|
| POST /api/tasks | 201 Created | `{ data: task }`, Location: `/api/tasks/{id}` |
| PATCH /api/tasks/:id | 200 OK | `{ data: updatedTask }` |
| DELETE /api/tasks/:id | 204 No Content | Пустое тело |

Создание:

```http
POST /api/tasks
Content-Type: application/json

{"title":"Подготовить защиту","priority":"high","categoryId":2}
```

Ожидаемое тело для первого POST после старта/reset:

```json
{"data":{"id":35,"title":"Подготовить защиту","completed":false,"priority":"high","categoryId":2}}
```

PATCH сохраняет непереданные поля. Например, `{"completed":true}` меняет только статус. DELETE возвращает 204 без JSON.

## Обработка ошибок

| Условие | Статус | Код |
|---|---:|---|
| Неверные поля или тип тела | 400 | VALIDATION_ERROR |
| Повреждённый или пустой JSON | 400 | INVALID_JSON |
| Неверный ID | 400 | INVALID_ID |
| Запись отсутствует | 404 | TASK_NOT_FOUND |
| Неизвестный путь | 404 | ROUTE_NOT_FOUND |
| Неподдерживаемый метод | 405 | METHOD_NOT_ALLOWED |
| Тело более 16 КиБ | 413 | PAYLOAD_TOO_LARGE |
| Нет application/json или неверная кодировка | 415 | UNSUPPORTED_MEDIA_TYPE |
| Неожиданная ошибка | 500 | INTERNAL_ERROR |

Пустое PATCH-тело запрещено. При POST/PATCH нужен Content-Type application/json. Поддерживается UTF-8. JSON-парсер ограничивает тело 16 КиБ. Сначала проверяется существование задачи, затем разбирается PATCH-тело; поэтому неверный или отсутствующий ID получает соответствующую ошибку раньше ошибки тела.

Если запись удалена после проверки requireTask, но до окончания чтения PATCH-тела, updateTask возвращает null и маршрут отвечает 404, а не восстанавливает удалённую задачу.

CORS разрешает GET, HEAD, POST, PATCH, DELETE и OPTIONS, а также заголовок Content-Type. Location открыт для чтения через `Access-Control-Expose-Headers`.

## Интеграция с React ПР8

Выполненный клиент ПР8 использует `useTaskData` и те же методы предметного API. Изменения выполняются пользовательскими действиями:
- submit формы вызывает POST или PATCH;
- переключение статуса вызывает PATCH только с completed;
- удаление вызывает DELETE;
- после успешной записи хук запускает GET с текущими фильтрами.

Кнопки блокируются во время pending, чтобы исключить повторные нажатия. При ошибке записи черновик формы остаётся, ошибка показывается отдельно, блокировка снимается. Если запись прошла успешно, но последующий GET завершился ошибкой, повторный POST не выполняется: сервер уже мог сохранить запись.

## Индивидуальный вариант 8

Фильтр варианта:

```js
{
  completed: "false",
  priority: "high",
  categoryId: "2"
}
```

Исходные подходящие ID: `[4, 34]`.

Сценарий:
1. Открыть клиент ПР8 с фильтром варианта 8.
2. Создать задачу с названием «Подготовить техническое руководство», priority high, categoryId 2.
3. Сервер назначает ID 35 и completed=false; после повторного GET видны [4, 34, 35].
4. Изменить статус ID 35 на completed=true.
5. После GET видны [4, 34], так как фильтр требует completed=false.
6. Открыть ID 35 по прямому запросу — задача существует и имеет completed=true.
7. Удалить задачу 35; повторный GET по ID возвращает 404.

Ожидаемая последовательность: **POST → GET → PATCH → GET → GET по ID → DELETE → GET по ID**.

## Проверка API напрямую

Создать файл `task.json` в UTF-8:

```json
{"title":"Проверить сервер","priority":"high","categoryId":2}
```

Выполнить:

```bash
curl -i -X POST "http://127.0.0.1:5505/api/tasks" -H "Content-Type: application/json" --data-binary "@task.json"
```

Использовать фактический ID из ответа:

```bash
curl -i -X PATCH "http://127.0.0.1:5505/api/tasks/35" -H "Content-Type: application/json" --data-binary "@patch.json"
curl -i -X DELETE "http://127.0.0.1:5505/api/tasks/35"
```

Файл patch.json содержит `{"completed":true}`. В PowerShell использовать `curl.exe`. Не подставлять ID 35, если фактический ответ сервера дал другое значение.

## Контрольные вопросы

1. **Почему сервер проверяет данные отдельно от формы?** Клиент можно обойти прямым HTTP-запросом; серверный контракт должен быть обязательным для всех клиентов.
2. **Чем PATCH отличается от полной замены?** PATCH изменяет только переданные поля, остальные сохраняет.
3. **Как отличить отсутствие поля от false?** Проверять наличие через Object.hasOwn, затем проверять тип boolean.
4. **Почему categoryId в JSON должен быть числом?** JSON имеет собственные типы; скрытое преобразование строки нарушило бы контракт.
5. **Почему nextId не равен длине массива?** После удаления размер массива уменьшается, а ID повторяться не должен.
6. **Что происходит после перезапуска сервера?** Память процесса очищается, восстанавливаются seed-данные.
7. **Почему POST возвращает 201 и Location?** Создан новый ресурс, а Location указывает его URL.
8. **Почему DELETE возвращает 204?** Операция успешна и дополнительное тело не требуется.
9. **Чем INVALID_JSON отличается от VALIDATION_ERROR?** Первое — тело нельзя разобрать; второе — JSON корректен, но структура или значения неверны.
10. **Как не допустить частичное изменение?** Сначала собрать все ошибки валидации, затем только при успехе вызвать store.
11. **Почему нельзя делать spread req.body без проверки?** Клиент мог бы перезаписать id и другие закрытые поля.
12. **Почему CORS не является авторизацией?** Он ограничивает доступ браузерному JavaScript, но не запрещает прямые HTTP-запросы.
13. **Зачем проверять updateTask после requireTask?** Запись могла исчезнуть во время получения тела запроса.
14. **Почему успех POST и сбой GET не одна неудачная операция?** Сервер уже мог создать ресурс; повтор POST способен создать дубликат.
15. **Что проверяют integration-тесты?** Реальный HTTP-контракт и адаптер клиента; интерфейс и браузерный CORS дополнительно проверяются вручную.

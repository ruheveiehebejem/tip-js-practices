## Вариант 8 — конкурентное удаление и PATCH

Сценарий моделирует гонку:
1. PATCH /api/tasks/4 проходит предварительную проверку существования задачи через requireTask.
2. Между проверкой и SQL UPDATE строка удаляется другим запросом.
3. UPDATE ... RETURNING не возвращает строку.
4. Store возвращает null.
5. Маршрут должен вернуть HTTP 404 TASK_NOT_FOUND, а не 200 и не пустой объект.

Файл tests/integration/variant-8.test.js воспроизводит эту последовательность управляемым fake store. Тест проверяет статус, код ошибки и details.id=4.

### Проверка мутацией

Чтобы убедиться, что тест действительно обнаруживает дефект, временно изменить обработчик PATCH в src/routes.js: удалить условие, которое проверяет результат store.updateTask на null, и оставить отправку ответа. Затем запустить:

    node --test tests/integration/variant-8.test.js

Ожидается, что тест упадёт: вместо требуемого 404 получит ответ с неправильным статусом/телом. После проверки вернуть исходный код и повторить тест: он должен пройти.

**Важно:** мутация не была применена к сохранённой ветке; исходный корректный guard оставлен в коде. Этот контрольный запуск нужно выполнить локально, он не должен попадать в финальный коммит.

## Качество кода

Настроены:
- ESLint через eslint.config.js;
- Prettier через prettier.config.js и .prettierignore;
- проверка тестовых файлов на todo, skip и only;
- Node.js test coverage с порогами 85% строк, 85% функций и 75% ветвей.

Команды:

    npm run format
    npm run format:check
    npm run lint
    npm run check:markers
    npm test
    npm run test:coverage
    npm run quality

Сначала npm run format форматирует рабочие файлы. Затем format:check проверяет, что форматирование не расходится с конфигурацией. lint запускает ESLint. check:markers запрещает отключённые и незавершённые тесты. test:coverage запускает unit и integration с порогами покрытия. quality объединяет проверки качества.

Покрытие относится к включённым src/**/*.js модулям; src/server.js и src/db.js исключены из инструментации в конфигурации проекта. Порог задаётся отдельно для строк, функций и ветвей; высокая доля строк сама по себе не гарантирует прохождение ветвей.

## PostgreSQL и переменные окружения

Для API использовать отдельную локальную учебную базу tip_tasks. Скопировать .env.example в .env и задать DATABASE_URL. Файл .env исключён через .gitignore и не коммитится.

Отдельная команда npm run test:db запускает тесты на реальной PostgreSQL. Тесты изменяют данные, выполняют reset и восстанавливают seed в finally. Не направлять DATABASE_URL на рабочую или чужую базу.

## Контрольные вопросы

1. Зачем нужны unit-тесты? Они проверяют небольшие функции изолированно от сети и БД.
2. Что проверяют integration-тесты? Совместную работу маршрутов, middleware, store и HTTP-ответов.
3. Почему тесты должны проверять ошибочные сценарии? Ошибка часто важнее обычного успеха: она не должна частично изменить данные.
4. Что такое граничный случай? Значение у предела допустимого диапазона или на границе состояний.
5. Что измеряет line coverage? Долю выполненных строк.
6. Что измеряет branch coverage? Долю проверенных направлений условных переходов.
7. Почему 100% строк не означает 100% ветвей? Условие могло выполниться только в одну сторону.
8. Для чего нужна мутация? Проверить, что тест действительно падает при внесении конкретного дефекта.
9. Что делает ESLint? Находит ошибки и несогласованные конструкции по правилам проекта.
10. Что делает Prettier? Приводит форматирование файлов к единому виду.
11. Зачем check:markers? Не позволяет случайно оставить незавершённый или отключённый тест.
12. Почему тесты БД выделены отдельно? Им нужна доступная PostgreSQL и отдельная база, которую можно менять.
13. Почему credentials нельзя коммитить? Они дают доступ к локальной или удалённой БД.
14. Почему store.updateTask может вернуть null после requireTask? Строку может удалить другой запрос между SELECT и UPDATE.
15. Почему в этом случае нужен 404? В момент выполнения UPDATE ресурс уже не существует, поэтому успешное обновление невозможно.

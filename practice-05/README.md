## Эксперимент с очередями выполнения

Перед запуском программы предполагалось, что сначала выполнятся синхронные сообщения, затем обработчики Promise и продолжение async-функции после await, а в конце задача таймера.

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Прогноз до запуска | A, B, C, D, E, F | Сначала синхронный код, затем микрозадачи, потом таймер |
| Фактический результат | A, B, C, D, E, F | Результат совпал с прогнозом |

Фактический вывод:

```text
A: синхронный код
B: начало async-функции
C: конец синхронного кода
D: обработчик Promise
E: продолжение после await
F: задача таймера
```

Объяснение:

- A, B и C относятся к синхронному коду и выполняются сразу.
- D выполняется как обработчик Promise и попадает в очередь микрозадач.
- E — продолжение async-функции после await, также выполняется как микрозадача.
- F относится к таймеру и выполняется после обработки микрозадач.

Таймер с задержкой 0 не выполняется немедленно, потому что его callback ставится в очередь задач таймера. Сначала JavaScript завершает текущий синхронный код и обрабатывает микрозадачи.

Если удалить обработчик Promise, сообщение D не появится. Продолжение после await и задача таймера останутся.

## Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Сервер API, обработка HTTP-запросов и выдача данных |
| `src/api-client.js` | Общий HTTP-клиент, выполнение запросов, обработка ошибок и JSON |
| `src/task-api.js` | Методы для работы с задачами и категориями, проверка ответов |
| `src/variant.js` | Номер индивидуального варианта и фильтры |
| `src/main.js` | Запуск клиентского сценария и вывод результатов |

`fetchFn` передаётся в `createApiClient`, чтобы клиент мог использовать переданную функцию для выполнения запросов. Это также позволяет проверять работу клиента с помощью тестовых функций.

HTTP-ошибки проверяются отдельно от сетевых. Например, ответ 404 означает, что сервер доступен, но запрошенный ресурс не найден. Сетевая ошибка возникает, когда запрос не может нормально связаться с сервером.

После разбора JSON данные дополнительно проверяются по контракту. Это нужно, чтобы программа не принимала неправильную структуру ответа за корректные данные.

## Последовательная и параллельная загрузка

Для сравнения использовались два запроса с задержкой 150 мс. Каждый сценарий был выполнен три раза.

| Сценарий | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Наблюдение |
|---|---:|---:|---:|---|
| Два последовательных `await` | 389,4 | 352,2 | 336,0 | Среднее время 359,2 мс |
| `Promise.all` | 154,4 | 157,2 | 162,4 | Среднее время 158,0 мс |

При последовательном выполнении второй запрос начинается только после завершения первого. Поэтому общее время увеличивается.

При использовании `Promise.all` оба запроса выполняются параллельно. Общее время получается меньше, потому что запросы не ожидают друг друга.

В проведённом эксперименте параллельная загрузка оказалась быстрее примерно в 2,27 раза.

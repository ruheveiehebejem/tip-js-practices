## Эксперимент с Event Loop

До запуска записать собственный прогноз. Для текущего примера ожидаемый порядок:

```text
A: синхронный код
B: начало async-функции
C: конец синхронного кода
D: обработчик Promise
E: продолжение после await
G: мой дополнительный обработчик Promise
F: задача таймера
```

Синхронный код выполняется первым. Затем обрабатываются микрозадачи: callback первого Promise, продолжение async-функции после await и добавленный callback G. Таймер выполняется после очереди микрозадач.

## Исследование API

При работающем сервере проверить следующие адреса:

| Запрос | Ожидаемый результат |
|---|---|
| `GET /api/health` | HTTP 200, JSON со статусом ok. |
| `GET /api/tasks` | HTTP 200, 12 задач, meta.total = 12. |
| `GET /api/tasks?completed=false&priority=high` | HTTP 200, подходящие невыполненные задачи высокого приоритета. |
| `GET /api/tasks/25` | HTTP 200, одна задача. |
| `GET /api/tasks/999` | HTTP 404 и код TASK_NOT_FOUND. |
| `GET /api/categories` | HTTP 200, три категории. |

Ответы успешных запросов содержат `Content-Type: application/json`. Для ошибок нужно отдельно посмотреть HTTP status, тело JSON и свойство `response.ok`. Ошибка HTTP 404 не является сетевой ошибкой: сервер доступен и вернул ответ, но запрошенная запись отсутствует.

Команда `npm run example:fetch` показывает свойства Response до разбора JSON.

## Реализация buildUrl и createApiClient

`buildUrl` принимает базовый абсолютный HTTP(S)-адрес, относительный путь и объект параметров. Путь присоединяется к базовому пути API без двойного слеша. Параметры кодируются средствами URLSearchParams. Значения undefined, null и пустая строка пропускаются, а false и 0 остаются в запросе. Входной объект не изменяется.

`createApiClient` возвращает метод `requestJson`. Он выполняет GET с заголовком Accept: application/json и сигналом отмены. При неуспешном HTTP-статусе создаётся ApiError с kind http и сохранением status, code, details и url. Для успешного ответа 204 возвращается null. Другой успешный ответ обязан иметь JSON Content-Type и корректное JSON-тело.

Ошибки разделяются:
- `http` — сервер вернул неуспешный HTTP-статус;
- `network` — fetch не смог получить ответ;
- `invalid-response` — ответ не является Response, имеет неверный Content-Type или повреждённый JSON;
- `timeout` — превышено заданное время;
- `aborted` — запрос отменён внешним AbortSignal.

Тайм-аут и внешняя отмена используют AbortController, но различаются по причине остановки.

## Предметный API задач

`createTaskApi` проверяет клиент, разрешённые фильтры, ID и структуру полученных задач и категорий. Коллекция задач обязана содержать массив data, корректный meta.total, корректные объекты и уникальные ID. Неверная схема приводит к ApiError с kind invalid-response.

`loadInitialData` запускает запрос задач и запрос категорий до ожидания Promise.all. Поэтому два независимых запроса выполняются параллельно. Искусственные задержки используются только в учебных экспериментах и не включены в рабочий код.

## Индивидуальный вариант 8

Методичка задаёт фильтр:

```js
{
  completed: false,
  priority: "high",
  categoryId: 2
}
```

Ожидаемые ID задач: `[4, 34]`, `meta.total = 2`. Фильтры применяются одновременно: задача должна быть невыполненной, иметь высокий приоритет и относиться к категории 2 («Проект»).

В `src/variant.js` установлен `variantNumber = 8` и соответствующий объект `variantFilters`. Ветвление по номерам вариантов не используется.

**Ожидаемый URL:** `http://127.0.0.1:5505/api/tasks?completed=false&priority=high&categoryId=2`.

## Обработка ошибок, тайм-аут и отмена

Проверить при работающем сервере:

- запрос задачи 999 возвращает ApiError kind http, status 404 и code TASK_NOT_FOUND;
- `/debug/error` возвращает HTTP 503 и kind http;
- `/debug/invalid-json` приводит к kind invalid-response;
- `/debug/text` приводит к kind invalid-response;
- задержка 150 мс при timeoutMs 20 приводит к kind timeout;
- внешний AbortController приводит к kind aborted.

После остановки API повторить `npm run client`: ожидается kind network. После запуска API повторить команду ещё раз и убедиться, что запросы снова выполняются.

## Собственные проверки

К официальному набору клиентских проверок добавлены три сценария:

1. Формирование URL с кириллицей, амперсандом и логическим false.
2. Повреждённое JSON-тело у HTTP 500 не должно менять тип ошибки с http на invalid-response.
3. Категории с повторяющимися ID должны отклоняться как неверный ответ.

## 3. Реализация

### 3.1. HTTP-клиент

В файле `src/api-client.js` реализован общий HTTP-клиент.

Он поддерживает следующие методы:

- GET — получение данных;
- POST — создание задачи;
- PATCH — частичное изменение задачи;
- DELETE — удаление задачи.

Для передачи данных используется JSON. При наличии тела запроса выполняется `JSON.stringify`, а также устанавливается заголовок `Content-Type: application/json`.

Для каждого запроса устанавливается заголовок `Accept: application/json`.

Реализована обработка следующих ситуаций:

- HTTP-ошибки;
- сетевые ошибки;
- некорректный JSON;
- неправильный Content-Type;
- превышение времени ожидания;
- внешняя отмена запроса.

Ответ со статусом 204 преобразуется в `null`, поскольку такой ответ не содержит тела и его нельзя разбирать через `response.json()`.

Для разных ситуаций используется класс `ApiError`, который хранит тип ошибки, HTTP-статус, код API, дополнительные сведения и URL запроса.

### 3.2. Доменный API

В файле `src/task-api.js` реализован модуль для работы с задачами и категориями.

Реализованы следующие функции:

| Функция | Назначение |
|---|---|
| `getTasks()` | Получение списка задач с фильтрами |
| `getTaskById()` | Получение отдельной задачи |
| `getCategories()` | Получение категорий |
| `loadInitialData()` | Параллельная загрузка задач и категорий |
| `createTask()` | Создание задачи |
| `updateTask()` | Редактирование задачи |
| `setTaskCompleted()` | Изменение статуса задачи |
| `deleteTask()` | Удаление задачи |
| `resetDemoData()` | Восстановление исходных данных |

Также реализована проверка структуры полученных данных. Проверяется наличие обязательных полей, правильность типов, допустимость приоритета и уникальность идентификаторов.

Функция `loadInitialData()` использует `Promise.all`, благодаря чему задачи и категории загружаются параллельно.

### 3.3. Состояния интерфейса

В файле `src/app-controller.js` реализовано управление состояниями приложения.

Используются четыре основных состояния:

| Состояние | Назначение |
|---|---|
| `loading` | Загрузка данных с сервера |
| `ready` | Данные успешно получены, список не пустой |
| `empty` | Запрос выполнен успешно, но задач нет |
| `error` | Возникла ошибка при загрузке |

При загрузке отображается сообщение о процессе выполнения запроса. Если задачи получены, отображается список. Если список пустой, появляется соответствующее сообщение.

При ошибке пользователь получает понятное описание и возможность повторить загрузку.

После изменения данных приложение повторно обращается к серверу и получает актуальный список.

### 3.4. Изменение данных

Реализованы основные операции управления задачами:

- создание новой задачи;
- редактирование названия, приоритета и категории;
- изменение статуса выполнения;
- удаление задачи;
- восстановление исходного набора данных.

Перед созданием и редактированием выполняется проверка формы.

После успешной операции приложение повторно загружает список задач с текущими фильтрами. Это позволяет отображать данные, подтверждённые сервером.

На время выполнения изменяющей операции кнопки блокируются. После завершения операции блокировка снимается.

Функция удаления поддерживает подтверждение действия через `window.confirm`.

### 3.5. Защита от устаревшего ответа

Для защиты от устаревших запросов используется `AbortController`.

Когда пользователь применяет новые фильтры, предыдущий запрос отменяется. Это необходимо, чтобы более старый ответ не перезаписал актуальный результат.

Дополнительно используется номер последовательности загрузки. Перед обновлением интерфейса проверяется, относится ли ответ к последнему запросу.

Если запрос был отменён или его результат уже устарел, интерфейс не изменяется.

Отмена запроса не отображается как обычная ошибка, поскольку в данном случае это ожидаемое поведение приложения.

## 6. Ответы на контрольные вопросы

**1. Почему `fetch` не отклоняет Promise при ответе 404?**

Потому что статус 404 является корректным HTTP-ответом сервера. Promise от `fetch` отклоняется при сетевой ошибке или отмене запроса. Поэтому необходимо отдельно проверять `response.ok`.

**2. Почему ответ 204 нельзя разбирать вызовом `response.json()`?**

Потому что HTTP 204 означает, что сервер успешно выполнил операцию, но не вернул тело ответа. При попытке разобрать пустое тело как JSON возникнет ошибка. Поэтому клиент возвращает `null`.

**3. Чем состояние `empty` отличается от `error`?**

`empty` означает, что запрос выполнен успешно, но подходящих задач не найдено. `error` означает, что запрос не удалось выполнить или сервер вернул ошибку.

**4. Зачем отменять предыдущий запрос при смене фильтров?**

Чтобы не обрабатывать устаревшие ответы. Например, если пользователь быстро применил несколько фильтров, старый запрос может завершиться позже нового. Отмена и проверка последовательности запросов предотвращают эту проблему.

**5. Почему после мутации список повторно запрашивается у API?**

Потому что сервер является основным источником данных. После создания, редактирования или удаления задачи приложение получает актуальный список с сервера и отображает подтверждённые изменения.


## HTTP-клиент

Клиент поддерживает только GET, POST, PATCH и DELETE. Для GET тело запрещено. Если тело есть, оно сериализуется через JSON.stringify и получает Content-Type: application/json. Для запросов без тела этот заголовок не добавляется.

HTTP-ошибка проверяется раньше Content-Type успешного ответа. ApiError сохраняет kind, status, code, details и url. Успешный 204 возвращает null и не вызывает JSON-разбор пустого тела.

Виды ошибок: `http`, `network`, `invalid-response`, `timeout`, `aborted`. Тайм-аут и отмена внешним AbortSignal классифицируются отдельно.

## Предметный API задач

Реализованы методы getTasks, getTaskById, getCategories, loadInitialData, createTask, updateTask, setTaskCompleted, deleteTask и resetDemoData. Каждый полученный объект проверяется до передачи интерфейсу. Для коллекций проверяются массив данных, meta.total и уникальность ID.

Удаление должно завершаться ответом 204 без тела. Сброс отправляется на POST /debug/reset и проверяет подтверждение сервера. После каждой успешной мутации контроллер повторно запрашивает список с действующими фильтрами.

## Валидация и карточки

Форма проверяется до отправки запроса. Название нормализуется через trim и имеет длину от 1 до 100 символов. Приоритет — low, medium или high. categoryId преобразуется в число и должен присутствовать в загруженных категориях.

Карточка содержит название, статус, приоритет, категорию и три действия: toggle, edit и delete. Пользовательские строки отображаются через textContent, поэтому текст с HTML-тегами не интерпретируется браузером как разметка.

## Контроллер и асинхронное состояние

Контроллер не обращается к document. Он хранит текущие задачи, категории, фильтры, режим редактирования и активную загрузку.

Состояния списка:
- loading — выполняется запрос;
- ready — список содержит задачи;
- empty — запрос выполнен успешно, но фильтр не нашёл записей;
- error — загрузка завершилась ошибкой, отображается возможность повтора.

При новой загрузке предыдущий запрос отменяется через AbortController. Дополнительно каждый запрос получает номер; результат применяется только при совпадении с последним номером. Поэтому старый ответ не перезаписывает результаты нового фильтра.

При успешной мутации кнопки блокируются, отправляется запрос на API, затем список повторно загружается. API остаётся источником истины; localStorage не используется для хранения задач.

## Индивидуальный вариант 8

Начальный фильтр по таблице вариантов:

```js
{
  completed: false,
  priority: "high",
  categoryId: 2
}
```

Ожидаемый исходный список: ID `[4, 34]`. Категория 2 называется «Проект». Фильтры применяются одновременно.

Индивидуальный сценарий:
1. Открыть `/?dataset=variant`, проверить две задачи.
2. Создать задачу с подходящими для фильтра параметрами: название «Подготовить техническое руководство», приоритет high, категория 2.
3. Проверить, что сервер назначил ID 35 и карточка появилась в текущей выборке.
4. Переключить задачу 35 в выполненное состояние.
5. Проверить, что после повторного GET задача 35 больше не отображается, поскольку начальный фильтр содержит completed=false.
6. Обновить страницу и убедиться, что сервер по-прежнему хранит созданную выполненную задачу.

**Ожидаемые ID:** до создания `[4, 34]`; после создания `[4, 34, 35]`; после переключения статуса `[4, 34]`.

**Фактические ID и результат после перезагрузки:** заполнить после ручного выполнения.

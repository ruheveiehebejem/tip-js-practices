## Цель и схема подключения

Заменить хранение задач в памяти на PostgreSQL, сохранив HTTP- и JSON-контракт ПР10. Клиент ПР8 должен продолжить работать с теми же маршрутами и полями.

Путь данных: React → Express API → PostgreSQL store → пул pg → PostgreSQL.

## Подготовка

Используется база ПР11 tip_tasks с таблицами public.categories и public.tasks. Перед запуском проверить, что в ней 3 категории и 12 задач. Не удалять неизвестные данные.

Скопировать .env.example в локальный .env и указать реальный пароль:

    API_PORT=5505
    DATABASE_URL=postgresql://tip_app:CHANGE_ME@127.0.0.1:5432/tip_tasks
    ENABLE_DEBUG_RESET=true

Файл .env содержит секрет и исключён через .gitignore. Пароль нельзя помещать в Git, скриншоты и отчёт.

Проверить node --version, npm --version и psql --version. Из папки practice-12 выполнить npm install, затем npm start. Требуется Node.js 24.x и PostgreSQL 18.x. npm install создаёт package-lock.json; сохранить этот файл для воспроизводимой установки.

## Запуск React-клиента

В локальном .env папки practice-08 указать VITE_API_URL=http://127.0.0.1:5505/api. В отдельном терминале из practice-08 выполнить npm ci и npm run dev. Клиент должен обращаться к API ПР12, а не к старым серверам ПР8/ПР10. Убедиться по DevTools Network, что запросы уходят на порт 5505.

## Пул соединений

В db.js создаётся один Pool на процесс. Ограничение пула — 5 соединений, connection timeout — 3000 мс. При запуске сервер выполняет SELECT 1 AS ok и начинает слушать HTTP-порт только после успешного соединения. При SIGINT/SIGTERM сначала закрывается HTTP-сервер, затем pool.end().

Health endpoint возвращает JSON со статусом ok и database=connected, не раскрывая пароль или строку подключения.

## Параметризованные запросы

В query-builders.js реализованы buildListTasksQuery и buildUpdateTaskQuery. Значения всегда передаются отдельным массивом values, а в тексте SQL используются плейсхолдеры $1, $2 и далее. Имена таблиц и колонок не приходят от пользователя.

В результирующем JSON сохраняется имя categoryId через SQL-алиас category_id AS "categoryId".

Список фильтруется в фиксированном порядке: completed, priority, categoryId, q. Поиск q сохраняет буквальную семантику ПР10: символы %, _ и обратная косая черта экранируются перед использованием ILIKE с ESCAPE. Поэтому эти символы трактуются как текст, а не как wildcard-шаблоны.

PATCH разрешает только title, completed, priority и categoryId. Порядок SET постоянный, ID — последний параметр WHERE. Проверка наличия поля выполняется через Object.hasOwn, поэтому значение completed=false не теряется. Пустой объект и неизвестные поля отклоняются до SQL.

## PostgreSQL store

Реализованы методы ping, listCategories, listTasks, getTask, createTask, updateTask, deleteTask и reset.

Создание использует INSERT с параметрами и RETURNING. Поле completed не передаётся, поэтому срабатывает DEFAULT false. ID назначается identity/sequence, а не рассчитывается в JavaScript. getTask и updateTask возвращают строку или null. deleteTask возвращает true только при rowCount=1.

## Транзакционный reset

Debug reset включается через ENABLE_DEBUG_RESET=true и предназначен только для локальной учебной среды.

Reset получает один client через pool.connect(), выполняет BEGIN, удаляет задачи и категории, вставляет 3 категории и 12 исходных задач, синхронизирует обе identity sequence через pg_get_serial_sequence и setval, затем COMMIT. При ошибке выполняется ROLLBACK. В finally всегда вызывается client.release(). Все команды транзакции выполняются на одном клиенте.

Результат reset: data.reset=true и data.total=12. Публичный reset нельзя включать в рабочем приложении без аутентификации.

## Ошибки базы данных

| Ситуация | SQLSTATE | Ответ API |
|---|---|---|
| Несуществующая категория | 23503 | 400 VALIDATION_ERROR |
| NOT NULL, CHECK, длина | 23502, 23514, 22001 | 400 VALIDATION_ERROR |
| Потеря соединения | класс 08, 57P01 | 503 DATABASE_UNAVAILABLE |
| Неожиданная ошибка | другие | 500 INTERNAL_ERROR |

Клиенту не отправляются SQL, stack trace, пароль, имена constraints и подробности драйвера. Предварительная валидация обеспечивает понятные ошибки, ограничения БД остаются второй линией защиты.

## Индивидуальный вариант 8

Начальная выборка: completed=false, priority=high, categoryId=2. Ожидаемые ID до добавления — [4, 34].

Сценарий:
1. Открыть React-клиент и проверить две задачи.
2. Создать задачу «Подготовить техническое руководство» с высоким приоритетом и категорией 2.
3. Записать фактический ID из ответа сервера; completed должен быть false.
4. Переключить новую задачу в выполненное состояние.
5. Перезапустить API и проверить, что новая запись сохранилась.
6. Получить её по ID и убедиться, что completed=true.
7. Удалить задачу и проверить ответ 404 при повторном GET.

Ожидаемая цепочка запросов: POST → GET → PATCH → перезапуск API → GET по ID → DELETE → GET по ID. Новый ID обычно будет больше 34, но точное значение необходимо брать из фактического ответа, поскольку sequence могла быть продвинута проверками.

Query-builder tests проверяют WHERE, порядок параметров, буквальный поиск и PATCH. Store tests проверяют SQL вызовы, RETURNING, rowCount, reset, rollback и release. API tests проверяют HTTP-контракт и ошибки. Database test проверяет полный CRUD на реальной PostgreSQL.

Официальный набор содержит 26 тестов. Database-тест может быть помечен skipped, если DATABASE_URL не задан, но это не заменяет обязательный запуск check:db. Тест изменяет учебную базу и восстанавливает исходный набор в finally; не запускать его на рабочей базе.

## Проверка постоянного хранения

Создать задачу через интерфейс, записать ID, остановить API через Ctrl+C, запустить снова и запросить запись по ID. Она должна сохраниться, поскольку хранится в PostgreSQL, а не в памяти Node.js.

Дополнительный пример npm run example создаёт задачу, сразу читает её и позволяет повторить запуск для проверки постоянства. Использовать только отдельную учебную базу.

## Контрольные вопросы

1. Зачем нужен пул? Для повторного использования ограниченного числа соединений.
2. Почему один Pool на процесс? Запросы используют общий управляемый пул.
3. Зачем параметры $1? Они отделяют значения от текста SQL.
4. Можно ли передать имя колонки через $1? Нет, имена выбираются из фиксированного списка.
5. Зачем categoryId алиасится? Сохраняется camelCase-контракт JSON.
6. Зачем экранировать q? Чтобы %, _ и обратная косая черта искались буквально.
7. Почему нельзя считать ID как max+1 в JS? Параллельные запросы могут получить одинаковый ID; sequence атомарна.
8. Зачем RETURNING? Новая или изменённая запись возвращается одним запросом.
9. Почему false проверяется через Object.hasOwn? False — допустимое значение, а не отсутствие поля.
10. Почему PATCH строится по allowlist? Клиент не может передать имя SQL-колонки.
11. Почему reset требует один client? Все команды транзакции должны выполниться на одном соединении.
12. Зачем finally release? Соединение возвращается пулу и при успехе, и при ошибке.
13. Чем 23503 отличается от 23514? Внешний ключ против CHECK.
14. Зачем БД повторяет валидацию? Категория могла исчезнуть после предварительной проверки.
15. Почему данные переживают restart API? Они хранятся в PostgreSQL.
16. Почему DB-тест нельзя направлять на рабочую базу? Он намеренно сбрасывает и изменяет строки.
17. Что если POST сохранился, а ответ потерялся? Повтор без idempotency key может создать дубликат.
18. Зачем graceful shutdown? Для закрытия HTTP-сервера и пула соединений.

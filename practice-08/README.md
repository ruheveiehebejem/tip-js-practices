## Контракт useTaskData

Хук вызывается как `useTaskData({ api, filters })`.

Он возвращает:
- `snapshot` — последний успешный объект `{ tasks, categories, meta }`; начальное состояние содержит пустые массивы и `meta.total = 0`;
- `status` — `loading`, `ready` или `error`; пустой успешный результат остаётся `ready`;
- `error` — ошибка чтения или null;
- `mutationError` — отдельная ошибка записи или null;
- `pending` — выполняется ли мутация;
- методы `refresh`, `saveTask`, `toggleTask`, `deleteTask`, `resetData`.

## Эффект загрузки и его зависимости

Загрузка запускается в `useEffect`. Перед каждым запросом создаётся свой AbortController. Cleanup сначала помечает конкретный запуск неактуальным, затем отменяет его. Запись результата разрешена только пока локальный признак актуальности равен true.

Зависимости эффекта: стабильный `api`, примитивные значения `q`, `completed`, `priority`, `categoryId` и счётчик `revision`. Сам объект filters и результат snapshot не добавляются в зависимости: объект может создаваться заново на каждый рендер, а изменение снимка не должно само запускать GET.

Каждый запрос вызывает `api.loadInitialData({ q, completed, priority, categoryId }, { signal })`. Задачи и категории загружаются параллельно.

На время нового GET старый успешный снимок сохраняется. При успехе snapshot заменяется целиком, status становится ready. При ошибке актуального GET status становится error, но snapshot не очищается. Отменённая загрузка и запоздавшая ошибка не меняют состояние интерфейса.

## Мутации

POST, PATCH и DELETE запускаются из пользовательских методов хука, а не из эффекта. Общая функция мутации:
1. проверяет, что компонент смонтирован и другая запись не выполняется;
2. создаёт отдельный AbortController и немедленно сохраняет его в ref;
3. устанавливает pending и очищает mutationError;
4. выполняет операцию API;
5. при подтверждённом успехе увеличивает revision и возвращает true;
6. при ошибке сохраняет mutationError и возвращает false;
7. освобождает блокировку в finally.

`useRef` нужен для синхронной блокировки: один только setPending не препятствует двум вызовам до следующего рендера. При размонтировании активная мутация отменяется; после размонтирования состояние не обновляется и новый GET не запускается.

После успешной записи список перечитывается эффектом с актуальными фильтрами. Локальное добавление или редактирование snapshot не выполняется: сервер остаётся источником истины.

Ошибка POST/PATCH/DELETE не смешивается с ошибкой последующего GET. Если запись подтверждена сервером, но следующий GET не прошёл, метод мутации всё равно возвращает true; mutationError остаётся null, status становится error, а последний успешный снимок сохраняется. POST автоматически не повторяется, чтобы не создавать дубликат.

## Асинхронная форма и App

Форма ожидает Promise<boolean>. При true она очищает черновик создания или выходит из редактирования. При false оставляет введённые значения и показывает ошибку. На время записи поля и изменяющие кнопки блокируются.

App хранит снимок редактируемой задачи отдельно от текущей выборки. Поэтому изменение фильтра не уничтожает черновик, если задача исчезла из видимого списка. При PATCH из формы отправляются только title, priority и categoryId; completed не передаётся и сохраняет актуальное значение сервера.

Удаление подтверждается до запроса. При удалении редактируемой задачи форма возвращается в режим создания. Во время загрузки или ошибки GET изменяющие элементы отключаются, потому что последний показанный снимок может быть устаревшим.

## Индивидуальный вариант 8

Начальный фильтр:

```js
{
  completed: "false",
  priority: "high",
  categoryId: "2"
}
```

Ожидаемый начальный список: ID `[4, 34]`. Категория 2 — «Проект».

Сценарий:
1. Открыть приложение и проверить фильтр варианта 8.
2. Создать задачу «Подготовить техническое руководство», priority high, categoryId 2.
3. Сервер назначает ID 35, completed=false.
4. После POST выполняется GET с теми же фильтрами; видимые ID становятся `[4, 34, 35]`.
5. Переключить ID 35 в выполненное состояние.
6. После PATCH снова выполняется GET; ID 35 исчезает из выборки, потому что фильтр требует completed=false.
7. Обновить страницу: серверная запись существует, но не видна при данном фильтре, так как completed=true.

Ожидаемая последовательность запросов: **POST → GET → PATCH → GET**.

## Вывод

В работе реализован useTaskData для связи React с HTTP API. Разобрал, как useEffect запускает загрузку при изменении фильтров, зачем cleanup отменяет старые запросы и почему нужно отдельно игнорировать устаревшие ответы. Мутации выполняются по действиям пользователя, блокируются от повторного запуска через useRef и после успеха инициируют повторный GET. Ошибка чтения не стирает предыдущие успешные данные, а ошибка мутации хранится отдельно.

## Контрольные вопросы

1. **Зачем загрузка находится в useEffect?** Потому что запрос синхронизирует React с внешней системой, а не вычисляет JSX.
2. **Когда срабатывает cleanup?** Перед повторным запуском эффекта с новыми зависимостями и при размонтировании.
3. **Почему callback эффекта не async?** React ожидает функцию очистки или undefined, а не Promise.
4. **Почему snapshot не в зависимостях?** Иначе результат GET сам вызовет новый GET.
5. **Зачем стабильный api?** Чтобы его новая ссылка не перезапускала эффект при каждом рендере.
6. **Зачем проверять active, если есть AbortController?** Не все реализации API немедленно прекращают работу после отмены.
7. **Почему проверка актуальности нужна в catch?** Старый запрос может отклониться после запуска более нового.
8. **Что проверяет StrictMode?** Корректность пары setup/cleanup, повторно выполняя цикл в разработке.
9. **Почему одного pending мало?** Два синхронных вызова могут начаться до следующего рендера; ref меняется сразу.
10. **Что означает true от saveTask при неуспешном GET?** Сам POST/PATCH подтверждён сервером; ошибка относится к обновлению списка.
11. **Почему нельзя автоматически повторять POST?** Первый запрос мог сохраниться на сервере, а ответ потеряться; повтор создаст дубликат.
12. **Почему смена фильтра не отменяет мутацию?** Фильтр относится к чтению; изменение записи должно завершиться независимо от нового GET.
13. **Что происходит при отмене ожидания?** Клиент перестаёт ждать, но уже выполненное сервером изменение не откатывается автоматически.
14. **Что означает meta.total?** Количество записей в текущей отфильтрованной выборке.
15. **Что не проверяет jsdom?** Реальный CORS, внешний вид в браузере, DevTools Network и фактическую работу пользователя с клавиатурой.
